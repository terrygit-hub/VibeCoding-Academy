Chapter 6 · 第 6 章

开发流程全景

c62a9f4 · ch6main

回看你走过的五章：其实你一直在转同一个圈——需求 → AI 生成 → 审查 → 验证 → 提交。这一章把这个圈挑明、补全最后两块短板（系统的验证、里程碑存档），再用一次彻底的「数据体检」把 2024 年数据里最后的雷全部排掉。

⏱ 约 45 分钟 · 前置：第 5 章

01五步循环：你和专业团队转的是同一个圈

专业软件团队迭代一个产品，无论做 App 还是做银行系统，拆开来都是这五步：

类比时刻：一桌完整的菜

餐厅出好一桌菜，靠的从来不是厨神，而是流程：点单（需求——写清楚，别喊「随便」）、后厨开火（AI 生成）、厨师长试味（审查——咸了淡了一口就知道）、核对菜单上菜（验证——点的 8 道一道不能少）、记账出单（提交——这桌完了才能翻台）。前五章你在学「点单」和「开火」，这一章补上「试味」「核单」和「记账」——凑齐完整的一桌。

五步里你已经很强的是①②（咒语四件套、小步迭代），做过但不成体系的是③④（第 2 章的三个万能追问、Excel 手算对答案），第 3、5 章覆盖了⑤的一半（commit / push）。本章把③④⑤拧成正式的制度。

02审查：三个问题看穿 AI 的活

审查不是逐行读代码——那是程序员的事。你的审查是质询：东西做完了，先别急着用，问它三个问题（第 2 章的三个万能追问，正式上岗）：

用大白话讲讲你刚写的这段做了什么，假设我完全不懂编程。

三件事：读表；按「订单日期」列取出月份分组求和；把每月合计画成条形图。没有做任何删除或修改数据的操作。

你做了哪些假设？

三个：假设金额列没有空值；假设所有日期都在 2024 年；假设同一笔订单不会重复出现。如果假设不成立，结果会偏。

第三个假设我不放心——这是多人录入的销售流水。如果数据里有重复订单，你的结果会怎样？怎么发现？

重复会被重复计账，总额虚高，肉眼看不出来。可以写个检查脚本自动核对——这就做。

三问的顺序有讲究：先懂（它做了什么）→ 再疑（它假设了什么）→ 后攻（哪个假设最可能塌）。第三问直接引出了本章的主角——验证不能靠眼睛，得靠证据。

03验证：从「看一眼」到「体检报告」

到目前为止你的验证是「打开页面看一眼 + Excel 手算抽查」。人肉抽查没错，但抽不完 1006 行。专业做法：让 AI 写一个「体检脚本」，把业务规则逐条变成自动检查，一秒钟扫完全表。在 example 目录对 AI 说：

写一个数据体检脚本 data_check.py 检查 data/sales_2024.xlsx，逐项报告：① 整行完全重复的订单（列出订单编号）；② 金额 ≠ 数量 × 单价的行（业务规则：金额 = 数量 × 单价）；③ 每列缺失值数量；④ 订单日期列里文本格式的行数；⑤ 产品类别出现的所有取值。用 ✅/⚠️/❌ 标注严重程度，中文输出。只检查、不修改数据。

已写好 data_check.py（只读不改）。运行体检：

📋 数据体检报告 · sales_2024.xlsx
共 1006 行 × 10 列

=== ① 重复订单 ===
❌ 发现 6 组整行完全重复（12 行）：SO-2024-0120 / 0260 / 0400 / 0540 / 0680 / 0820

=== ② 金额校验（金额 = 数量 × 单价）===
❌ 8 行金额对不上：SO-2024-0066 录的 ¥2,558.40 应为 ¥3,198.00（其余 7 笔类似，多为少录两三成）

=== ③ 缺失值 ===
⚠️ 地区：缺 12 行 · 城市：缺 12 行

=== ④ 日期格式 ===
⚠️ 59 行日期是文本（如 2024/3/5）

=== ⑤ 类别口径 ===
⚠️ 出现 6 个类别：标准 3 类之外混有简称「文具 14 / 设备 13 / 消耗品 13」

五颗雷全部现形：①②是本章新爆的两颗（重复计账、金额录错），③④⑤是第 2、4 章已排过的三颗（脚本顺带复查——好的体检从来不嫌啰嗦）。这份报告就是下一步的输入。

体检脚本是「一次性」的吗？

不是——把它留在项目里，数据每次更新都重跑一遍。它就是你的质检工位：不产生结论，只陈述事实；不修改数据，只报告问题。以后 AI 改任何分析代码，你都能用同一份体检报告对照「底数」有没有被动过。

04裁决：五份问题，五个口径

体检报告躺在那里不会自己变好。每一项怎么处理，都是业务决定——裁判只能是你。拿销售流水来说，合理的裁决长这样：

体检发现裁决理由
❌ 6 组整行重复删除，每组保留第一笔订单编号一样、每个字段一样 = 重复录入，不是真实卖了两次
❌ 8 笔金额对不上按 数量 × 单价 重算真值只有原始凭证知道；业务规则摆在那，重算值比错的录入值更可信
⚠️ 12 行缺地区归入「未填写」第 4 章已定的口径，保持不变（宁可见，不可删）
⚠️ 59 行文本日期解析成真日期第 2 章已定的口径
⚠️ 40 行类别简称按映射归并第 2 章已定的口径

注意前两条的原则：删除和改数是最重的两招，必须一条一条给出理由，绝不「让 AI 自己看着办」。裁决完毕，把整张表连口径一起交给它执行——关键要求：原始文件一个字不动，清洗结果另存新文件（原始数据永远可追溯）：

按以下口径清洗 data/sales_2024.xlsx，另存为 data/sales_2024_clean.xlsx，原始文件不动：① 删除整行重复，保留第一笔；② 金额按 数量×单价 重算；③ 缺失地区/城市填「未填写」；④ 文本日期解析为真日期；⑤ 类别简称按映射归并为三大类。清洗后用 data_check.py 体检新文件，确认全部 ✅。

清洗完成：sales_2024_clean.xlsx 共 1,000 行。复检新文件：① 无重复 ✅ ② 金额全部相符 ✅ ③ 无缺失 ✅ ④ 全部真日期 ✅ ⑤ 三个类别 ✅。另建议把看板的数据源改为清洗后文件。

把看板（dashboard.py）的数据文件换成清洗版，刷新页面——数字变了：1,006 笔 → 1,000 笔，总销售额 ¥1,108,140 → ¥1,109,725。总额不降反升？说得通：去掉 6 笔重复（-¥1,618），8 笔录错的金额按规则重算（7 笔少录、1 笔多录，净增 +¥3,204），合计净增约 ¥1,585。数字变了不可怕，可怕的是说不出为什么变——你现在说得出了，这就是口径的力量。

05提交：里程碑打 tag

一圈走到⑤。这次的提交比往常多两样：清洗脚本产出的新数据、体检脚本本身——它们和看板一样是项目资产。存档之外，再学最后一招：tag（标签）——给某个存档点起个正式名字，当作里程碑：

终端 · 在你的项目根目录（example 里干完活，/exit 后回到根目录）
# ① 常规存档：体检脚本 + 清洗数据 + 看板换数据源，一起打包
git add example/data_check.py example/data/sales_2024_clean.xlsx example/dashboard.py
git commit -m "数据体检与清洗：去重6笔、金额重算8笔，看板改用清洗版"
# ② 给这个存档点钉一个里程碑名字（tag 只是个名字，不占空间）
git tag data-clean-v1
# ③ push 默认不推 tag，要单独说一声
git push && git push --tags
Total 0 (delta 0), reused 0 (delta 0)
To github.com:你的用户名/vibe-coding-academy.git
 * [new tag]           data-clean-v1 -> data-clean-v1

以后任何时候，git tag 一列，里程碑一目了然（你克隆课程时自带的 ch0-setup、ch1-done……就是课程自己的里程碑）。想看某个里程碑时的代码：git checkout data-clean-v1（第 3 章的「观光模式」）。

五步都齐了，圈转起来了

回头看这一章干的事：需求（体检）→ AI 生成（data_check.py）→ 审查（三问挖出重复风险）→ 验证（体检报告 + 复检全绿）→ 提交（存档 + tag）。你没有学新魔法，你把旧招式排成了阵。这就是「开发流程」的全部真相——一个被纪律串起来的循环。

06课后三件套

动手做：给体检加一项「防未来」检查

现在这份体检查的都是已经发生的问题。给它加一项面向未来的检查：数量或单价 ≤ 0 的行（真实业务里可能是退货冲账录成了负数、或漏填录成了 0）。当前数据里没有这种行，所以新检查应输出 ✅——写完自己验证这一行真的输出 ✅。

点开看参考咒语

给 data_check.py 加第 ⑥ 项检查：找出 数量 ≤ 0 或 单价 ≤ 0 的行列出订单编号，没有则输出 ✅。改完运行一遍，确认新增项输出 ✅ 且原有各项结果不变。

已加第 ⑥ 项，运行输出「✅ 无异常数量/单价」，原 ①–⑤ 项结果与上次完全一致。

「原有各项结果不变」这句验收很重要——改检查工具本身，不能顺手把别的检查改坏了。工具也要被验证，这就是循环的纪律。

自测 3 题（点击展开答案）

1. 五步循环是哪五步？你在第 1 章其实已经转过第一圈，对号入座一下？

需求 → AI 生成 → 审查 → 验证 → 提交。第 1 章：念咒语（需求）、AI 写 ch1_report.py（生成）、听它汇报干了什么（审查）、双击打开看数字（验证）——只差「提交」没做（那时你还没学 git，第 3 章才补上）。

2. 审查三问的顺序为什么是「先懂、再疑、后攻」？

先懂它做了什么（否则你连质疑的资格都没有），再问它假设了什么（假设是错的藏身处），最后挑最可疑的假设主动攻击（「如果数据有重复会怎样」）。反过来问——上来就攻——你分不清它是真稳还是嘴硬。

3. 为什么验证要写成体检脚本，而不是每次用 Excel 手动抽查？

三个理由：脚本全量扫描，抽查永远有漏网；脚本可重复，数据每次更新一秒钟重跑，抽查坚持不了三次；脚本是证据，报告可以贴给老板/同事，口头说「我查过了」不算数。人肉抽查仍然该做——但作为脚本之外的最后一道，不是唯一一道。

翻车急救箱

① 清洗后看板打不开 / 报文件找不到
看板的数据路径没改过来或写错文件名。对 AI 说：「把 dashboard.py 读取的文件路径确认一遍，应为 data/sales_2024_clean.xlsx」。

② 清洗后数字变了，心里发慌
口径变了，数字就该变——慌是因为说不清差异。做减法：去重删了哪些（体检报告①）、重算改了哪些（②），两笔账算出来对上差值（本章是 +¥1,585），就敢签字。说清楚了，变比不变更可信。

③ tag 打错了名字 / 想删掉
本地删：git tag -d 名字；已经 push 过的还要删云端：git push origin :refs/tags/名字。重打：git tag 新名字。

④ git push --tags 报 everything up-to-date，但 GitHub 上没看到 tag
先 git tag 确认本地真的打上了；再看推送输出的目标是不是你自己的仓库（第 5 章换过 origin）。

⑤ 想回到清洗前的数据看看
原始文件 sales_2024.xlsx 一个字没动，双击就能看；看板想切回去，让 AI 把路径改回去再刷新。这正是「原始不动、另存清洗版」的红利。
